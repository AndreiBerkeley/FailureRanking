# GEPA_candidates — 12 instruction sets, one model

The candidate set `pool-3`: twelve four-module instruction sets proposed by a GEPA optimizer
run on hover (`plain_gepa_hover_seed0`), run by gemini-3.1-flash-lite. Eight were accepted
onto the optimizer's frontier and are taken at even intervals over its validation score;
four were rejected, also at even intervals — so the set spans the full score range.
`candidates/registry.jsonl` holds each candidate's four instruction texts, its acceptance and
validation score; `candidates/pool-3.json` the set and its rule.

## The current instrument (2026-09-17/18)

**Taxonomy tax-13 → tax-15-pool3.** `tax-13` was generated by the pipeline under
`GENERATION_v3.1` (`code/GENERATION_v3.md`) from 160 traces of 40 taxonomy-pool tasks, one
refinement round, a four-reader gate, a 50-trace gap test, granularity splits and the
proposal stage — no hand codes; 13 codes, 8 domain and 5 general (gates: kappa 0.66 → 0.62,
coverage 0.98; `taxonomy/tax-13/README.md`). The judge run under it kept 170 points that fit
no code, 138 of them unrecovered — 16% of that run's unrecovered evidence. Read by hand they
were two mechanisms, and `tax-15-pool3` adds them as `SP_14` (a query issued for a known
required page that retrieval does not return — bundled with already-resolved terms, too
broad, neighbours ranked above it) and `SP_15` (the summary leaves a required document
unidentified). `taxonomy/tax-15-pool3/assignments.json` maps the uncoded points by turn kind
(132 → SP_14, 31 → SP_15, 7 set aside); no re-judge, so SP_14/SP_15 rates are the decider's
"nothing fits" points, not a pass with the codes in view. Stated as the limitation it is.

**Judge (two readers + decider, "pointjudge").** Reader A reads with the taxonomy, reader B
with none; each lists failure points (turn, verbatim evidence, one-sentence problem), then
assigns codes to its own points; a decider validates every point against the trace, merges
duplicates, and settles the codes. Readers `openai/gpt-5.6-luna`, decider `openai/gpt-5.6-sol`
(both via OpenRouter, reasoning high), 3,043 points on 600 traces, 735 reader points rejected
by the decider, 0 traces failed; $65. Every pass has the program's **success rule** in view —
`hover/program/structure.json` `success_rule`: the output is scored on the titles of the
retrieved documents, three per task; a mention inside another document does not count. It is
the task's scoring definition, not any task's gold. Design: `code/pointjudge_design.md`.

**Recovery pass.** A separate reader (`anthropic/claude-sonnet-5`, reasoning high) takes each
trace with its judge points, codes hidden, and answers four anchored questions per point
(what the point produced, which later turns consumed it, what later turns did about it, and
whether the final output carries its effect or lacks what it cost); every quote is checked
against the trace and the verdict is computed by a fixed rule: unrecovered / corrected /
contained / made_irrelevant. With the success rule in view: 839 of 3,043 points unrecovered
(28%); $77. A hand audit of 60 recovered and 20 unrecovered verdicts found 2 and 0 wrong
(`results/explored-formulas.md`). `code/new_pipeline/recovery/README.md` has the design.

**Coverage.** Of the 274 traces that fail on gold, 271 carry at least one point and 238 carry
an unrecovered point; of the 326 that pass, 18 carry an unrecovered point. Gold is used here
only to report coverage, never in a scoring path.

**Two judged sets, 100 tasks, one taxonomy, one judge.** `eval-1/sample` (50) and
`judging-sample-2` (50) are disjoint from each other and from the 500-task `eval-1/domain`
that serves as gold-gen. `judging-sample-2` was drawn stratified by the tasks' mean
candidate score (four quartiles), so its gold-50 read outcomes at draw time; the sample was
not. Both are stated in the results.

**Taxonomy tax-10.** Ten codes (4 general, 6 domain) — output form breach, missing required
part, wrong content in field, unsupported assertion, premature completion, input misreading,
unlicensed conclusion, work state misjudged, misdirected next step, missing closing marker —
re-levelled by hand from an 18-code induced taxonomy so that every code names a mechanism any
candidate could exhibit; `taxonomy/tax-10/README.md` records the review that motivated it.

**Judge (panel + open reader).** Per trace: two annotators (gemini-3.6-flash, thinking high,
temperature 0) each read with the taxonomy and name the codes; a code fires when both agree.
An open reader (gemini-3.1-pro-preview) reads with no taxonomy and reports problems, mapped
to codes afterwards. `judge/mapping.jsonl` gives per trace the codes that fired and which
source supplied each; `judge/judge_records/` the full record per trace; `judge/manifest.json`
the settings, per-code firing and audits. The per-trace mapping carries counts, not steps;
the step-attributed methods read the judge records instead — `votes_by_turn` (which turn each
annotator reported a code at) and the open reader's problems with their agent — and place
each counted code at the turns it was reported. 600/600 judged, 0 failed, in both sets.

**Traces.** One JSON per trace, the outcome-blind judge view (`messages` = the DSPy turns as
rendered for the judge; `metadata` = task, candidate, candidate index, split). Gold is in
`outcomes/`, keyed by trace id, candidate and task.
